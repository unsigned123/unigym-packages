# M0 design brief: test-pack plugin and basic pack

## Goal

Prove the test-pack contract with an independent workspace:

- a `unigym-test-packs` pytest plugin that discovers installed packs from the
  `unigym.test_packs` entry-point group;
- a `unigym-test-pack-basic` content distribution whose wheel carries its pack
  root;
- marker, fixture, availability, strict-mode, wheel and boundary contracts.

## Non-goals

- No cartpole or G1 assets.
- No code packs.
- No core repository changes or core test migration.
- No pack-to-pack dependencies or production pack discovery.
- No large-asset artifact or publication policy.

## Files

```text
pyproject.toml                         workspace, lint/tooling, import contracts
packages/unigym-test-packs/            plugin distribution
packages/unigym-test-pack-basic/       first content pack
tests/unit/                            pure discovery/marker logic
tests/contract/                        plugin behavior and environment coercion
tests/consumer/                        installed basic-pack consumption
tools/check_wheel.py                   isolated installed-wheel acceptance
docs/design/m0.md                      this brief
```

## Classes, protocols and registries

- `PackIndex`: immutable installed pack name -> root mapping.
- `PackDiscoveryError`: installed pack metadata or manifest is broken.
- `marker_requirement(item)`: validates the single
  `requires_test_packs(...)` marker and returns declared pack names.
- Plugin fixtures: `pack_root(name)` and `pack_runtime(*names)`.
- No registry is added to core. The entry-point group is the only discovery
  source.
- Owner of installed metadata validation: `discovery.py`.
- Owner of marker syntax: `markers.py`.
- Owner of pytest lifecycle and fixture wiring: `plugin.py`.
- Owner of pack manifests: the core `unigym.pack/1` loader through
  `unigym.pack_api.load_manifest_v1`.

## Interactions and data flow

1. `pytest_configure` reads installed entry points once and validates every
   target and manifest. A broken installed pack fails configuration.
2. `pytest_runtest_setup` validates the item marker. Missing packs skip by
   default or fail under `--strict-test-packs`.
3. `pack_root(name)` checks that `name` is declared by the item and returns the
   installed root.
4. `pack_runtime(*names)` checks declarations, then calls
   `unigym.pack_api.discover(roots=[...])`. Results are cached per pack tuple in
   the pytest config.
5. Activation remains explicit through the returned `PackRuntime`.

## Invariants and failure modes

- The plugin never reads `UNIGYM_PACKS` or `UNIGYM_DEPS_ROOT`.
- Entry-point name must equal manifest `name`.
- A target must resolve to an absolute existing pack root; a callable target is
  called exactly once at configuration.
- Marker: exactly one per item, at least one argument, unique arguments matching
  `^[a-z][a-z0-9_]*$`, no keyword arguments.
- A fixture request for an undeclared pack fails; a missing declared pack skips
  or fails according to strict mode.
- A broken installed pack fails at configuration, not as a per-test skip.
- Runtime activation is never implicit.
- Import boundaries are enforced with import-linter.

## Compatibility and migration

- Public API impact: none in core.
- Schema impact: none; packs use `unigym.pack/1`.
- Dependency impact: plugin requires `unigym>=0.106,<1` and pytest; the local
  workspace overrides core with `../unigym-core` for development.
- Migration: none; M1 starts core migration.

## Tests

- Lowest layer: pure discovery and marker tests under `tests/unit`.
- Pytest lifecycle and availability behavior: `pytester` contract tests.
- Installed content pack: consumer tests with
  `pytest.mark.requires_test_packs("basic")`.
- Wheel: `tools/check_wheel.py` builds wheels and runs a consumer test in an
  isolated environment outside the checkout.
- Boundary: import-linter plus a poisoned-environment test.
- Fast-suite impact: no core fast lane exists here; pack-dependent tests are
  explicitly marked, so callers can deselect `requires_test_packs`.

## Risks and open questions

- Risks: `uv run --isolated` cache/offline behavior; editable core discovery in
  local wheel checks; future large-pack wheel size.
- Alternatives considered: ambient environment discovery (rejected); core
  entry-point group reuse (rejected); automatic pack activation (rejected).
- Open questions: none block M0. Large-asset and publication decisions remain
  deferred to M1/M2.
- Rollback path: delete the independent repository; core is unchanged.
